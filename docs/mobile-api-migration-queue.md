# Mobile API Migration — Task Queue

Living checklist consumed by the `mobile-api-migration` cloud routine. Each 5-hour firing:

1. Reads this file, finds the **first unchecked task** it's allowed to attempt (see gating rule below).
2. Branches off **`mobile-api/phase-0-foundation`** — the single feature/integration branch for the entire migration — as `mobile-api/<task-slug>`.
3. Implements it using the **extract-shared-lib pattern**: pull the core logic into a plain function under `lib/`, replace the existing Server Action's implementation with a call into that shared function (its public interface and call sites in the web app are unchanged, so web behavior doesn't regress), and add a new `app/api/v1/**/route.ts` that wraps the same function with bearer-token auth. Never delete or rewrite the existing Server Action's external behavior. State the route's **error/timeout contract** in the PR description: which status codes it returns and when (auth failure, tenant mismatch, validation, upstream/DB failure), and whether the operation is retry-safe (GET routes are inherently retry-safe; mutating routes must state their idempotency behavior explicitly).
4. Adds/updates tests for the new route (auth: valid/missing/expired token; tenant isolation: a token for tenant A must never read/write tenant B's data), runs `typecheck`, `lint`, and the relevant test suite.
5. Commits, pushes the branch, opens a PR against **`mobile-api/phase-0-foundation`** — never against `main`. No task PR merges directly to `main`.
6. Marks the task `[~] PR open` below with a link to the PR (not `[x]`) and commits that checklist update directly to `main`. A task is only marked `[x] MERGED` once its PR is actually merged into `mobile-api/phase-0-foundation` — do not check a task complete just because a PR exists.
7. Stops. One task per firing.

**Gating rule (read before picking a task):** the integration base for every task in every phase is `mobile-api/phase-0-foundation`, full stop — branch off it, open every task PR against it. Do not target `main` for any task PR, and do not wait for [PR #28](https://github.com/suryatalamsevai/talam-web-app/pull/28) (the foundation branch → `main`) to merge before starting Phase 1+ work; that PR stays open until the whole feature branch has been deployed and verified (see "Promotion to `main`" below). This applies even if the Phase 0 pgbouncer spike-test checkbox below is still unchecked — that task is an infra verification, not a code dependency, and doesn't block Phase 1+.

Within a phase, task order doesn't matter — pick the first unchecked one.

**Checkout tasks (Phase 3) are payment-critical.** Use only the sandbox/test Razorpay keys already configured in the repo's env — never touch live credentials. Every Phase 3 PR description must open with `⚠ Payment-critical — manual QA in Razorpay sandbox required before merge`, and must pass an explicit security review before merge (bearer-token enforcement, tenant isolation, replay/idempotency protection reusing the existing Razorpay-order-id dedup pattern, webhook signature verification staying the single source of truth for payment state, input validation on coupons/quotes/uploads, and rate limiting) — do not fold this into general code review.

## Promotion to `main`

`mobile-api/phase-0-foundation` is the only branch this migration ever merges into `main`, via [PR #28](https://github.com/suryatalamsevai/talam-web-app/pull/28), and only once: every phase below is merged into it, the branch is deployed to a preview/staging environment (not production), the full test suite passes there, Razorpay-sandbox QA passes for every Phase 3 route, and a manual pass confirms bearer-token auth/tenant resolution/each `v1` endpoint behaves correctly. Any bug found during that deploy-and-verify pass gets fixed with a normal PR back into `mobile-api/phase-0-foundation`, then the branch is re-deployed and re-verified — only a clean pass is the green light to merge #28.
